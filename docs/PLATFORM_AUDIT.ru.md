## 2. Условной компиляции не существует

```console
$ grep -rn "__APPLE__\|__linux__\|__MACH__\|TARGET_OS\|_WIN32\|__unix__" cpp/
(совпадений нет)

$ grep -n "APPLE\|LINUX\|UNIX\|CMAKE_SYSTEM_NAME\|Darwin" CMakeLists.txt
(совпадений нет)
```

Одно дерево исходников, один рецепт сборки, обе платформы. Единственная строка во всём собственном
коде, знающая о платформе, — `bench/harness/manifest.py:44`:

```python
if sys.platform == "darwin":
```

— выбирает способ прочитать модель CPU для манифеста прогона. Это ветка *отчётности*, а не кодовый
путь в чём-либо измеряемом.

**Следствие:** различие в поведении между macOS и Linux **не может** объясняться по-разному
скомпилированными путями. Гипотеза устранена, а не просто маловероятна.

### 2.1 Но бинарники не идентичны

Совпадение на уровне исходника — не совпадение бинарников. Сборки различаются по четырём
независимым осям:

| | Хост macOS | Контейнер Linux |
|---|---|---|
| Компилятор | Apple clang 21.0.0 (clang-2100.1.1.101) | GCC 15.2.0 (Ubuntu 26.04 LTS) |
| Формат объектов | Mach-O 64-bit arm64 | ELF aarch64 |
| libc / аллокатор | Apple libc, libmalloc | glibc, ptmalloc2 |
| Ядро | Darwin 26.5.2 | Linux 6.12.76-linuxkit |

Это важно для §6: сравнение «нативно против контейнера» меняет все четыре сразу, поэтому оно не
изолирует одну причину. На более узкий вопрос оно всё же отвечает — он сформулирован там же.

## 3. Поверхности тестирования — задействованы обе платформы

| Цель | Платформа | Содержимое |
|---|---|---|
| `make fast` | macOS arm64 | dev-набор C++ + набор Python, оба свежесобранные |
| `make check` | macOS arm64 | lint, mypy, format, матрица 4 пресетов, coverage, docs |
| `make test-all` | macOS arm64 | пресеты dev / rel / **asan** / **tsan** |
| `make verify-linux` | Linux aarch64, закреплённый образ | Официальный контейнерный гейт |
| `PLATFORM=linux/amd64` | Linux x86-64 под qemu | Кросс-архитектурный smoke |

Нативные бинарники macOS существуют для каждого пресета и проверены:

```console
$ file -b build/rel/mm_engine
Mach-O 64-bit executable arm64
$ file -b build/asan/mm_engine
Mach-O 64-bit executable arm64
$ file -b build/tsan/mm_engine
Mach-O 64-bit executable arm64
```

Покрытие гейтится на `fail_under = 100` для пакета `mmclient`
(`python/pyproject.toml:157`). Корпус тестов: 17 модулей Python, 24 единицы трансляции C++.

**О переносимости санитайзеров.** ASan на платформах Apple **не поддерживает** LeakSanitizer
(`detect_leaks=1` → «not supported on this platform»), тогда как внутри Linux-ASan LSan включён по
умолчанию. Хост macOS поэтому структурно неспособен увидеть класс дефектов, который видит
контейнерный гейт Linux. Это известная асимметрия, а не пробел в дизайне тестов — именно поэтому
официальным является контейнерный гейт.

## 5. Поправка — заявлен механизм, который не измерялся

Ранее в этом проекте утверждалось, что спорадические многомиллисекундные остановки происходят из
виртуальной машины Docker Desktop. **Это утверждение не подкреплено измерением.** Все три матрицы
сняты внутри VM; ни одного прогона вне её не существует; следовательно, сравнения не было.

Что произошло на самом деле: две конкурирующие гипотезы были опровергнуты, а третья — как
последняя невыбывшая — подана так, будто она установлена. Устранение альтернатив не есть
доказательство остатка.

Доказательная база с разделением по статусу:

| Статус | Утверждение | Основание |
|---|---|---|
| **ДОКАЗАНО** | Средняя нагрузка хоста не предсказывает загрязнение | Загрязнение при нагрузке 4.14, ниже порога отказа 8.0 |
| **ДОКАЗАНО** | Увеличение выборки не стабилизирует p99.9 | Остановки нестационарны; больший *n* разбавляет всплеск, но не убирает его |
| **ДОКАЗАНО** | Бинарник движка постоянен между матрицами | Идентичный `engine_sha256` |
| **ДОКАЗАНО** | Условной компиляции не существует | §2 |
| **НАБЛЮДЕНО** | Кластеры многомиллисекундных остановок примерно через 7 минут после старта, на в остальном простаивающей машине | `idle_tuned_R1`: 187 замеров > 1 мс в 11 окнах, максимум 61.6 мс, wall 11.014 с против 9.403 с у соседа |
| **НАБЛЮДЕНО** | Апостериорный peer-аудит отделяет возмущённые прогоны от чистых | Отметил ровно `idle_tuned_R1`, пропустил остальные 21 |
| ~~ВЫВОД~~ → **ОПРОВЕРГНУТО (2026-07-31)** | Что источник — именно VM | Нативный прогон §6.1 тоже даёт остановки — феномен уровня хоста |

Это тот же класс ошибки, который прямо назван в рабочих правилах проекта: *не заявлять механизм,
которого не измерял*. Средство в §6 — измерение, а не переформулировка.

## 6. Решающий эксперимент

`scripts/run_bench.sh` работает на macOS нативно без правок — его чтения `/proc` защищены
(`[[ -r /proc/1/cgroup ]] || return 1`, `nproc 2>/dev/null`), и `make bench-smoke` уже гоняет его на
хосте.

**Процедура:** снять ту же матрицу (3 повтора × 100 000 замеров × 6 ячеек) нативно на хосте macOS,
против `build/rel/mm_engine`, и сравнить профиль выбросов.

| Исход | Толкование |
|---|---|
| Нативный прогон чист | Остановка следует за VM. Утверждение становится измеренным. |
| Нативный прогон тоже даёт остановки | VM оправдана. Расследование переходит на наш код или на планировщик Darwin. |

**Заявленное ограничение, чтобы не перечитать результат.** Нативный прогон меняет компилятор,
формат объектов, аллокатор и ядро одновременно (§2.1). Он отвечает на вопрос *«остановка следует за
VM или за кодом?»* — он **не** изолирует единственную причину. Полностью изолирующий тест требует
нативной машины Linux, которой здесь нет.

**Эти числа не станут публикуемыми.** Спецификация требует закреплённый контейнерный образ;
нативный прогон — только диагностика.

**Порядок.** Нативный прогон нельзя запускать, пока идёт контейнерная матрица — второй бенчмарк
поверх работающего есть ровно то загрязнение (№4 из пяти), из-за которого появился lock матрицы.
Очерёдность: контейнерная матрица → peer-аудит → нативная диагностика.

### 6.1 Исход (2026-07-31) — сработала вторая ветка

Нативная матрица (run id `20260731T043914Z`, 3 повтора × 6 ячеек, хост macOS, нативный
`build/rel/mm_engine`, только диагностика — публикации не подлежит по правилу) **тоже даёт
остановки**. Её сырые серии утилизированы после извлечения в таблицу ниже — по правилу,
что диагностический материал не хранится после переработки:

| группа | нативный профиль | контейнерный профиль (7-повторная матрица) |
|---|---|---|
| idle | идеально чист — 0 выбросов во всех 6; wall **на 35% быстрее** (6.07 с против 9.3 с) | чист |
| paced naive | `R1` несёт **1 392** замера >5 мс в 7 окнах | худший повтор нёс 35 |
| react | выбросы 11–180 в **каждом** прогоне (медианы соседей 39/16) | 1–7 выбросов |
| флаги аудита | `paced_naive_R1`, `react_naive_R1` | 2 из 42 |

По таблице решений выше срабатывает вторая ветка: **VM оправдана как источник.** Кластеры
многомиллисекундных остановок происходят и нативно на macOS — феномен следует за хостом, а не за
VM. Общий фактор — десктопная ОС без изоляции ядер; какая именно подсистема хоста (миграция
планировщика по P/E-ядрам, power management, коалесценция таймеров) — этим экспериментом **не
изолировано**: он менял четыре переменные разом, ровно как заявлено в ограничении выше, и назвать
одну из них причиной значило бы повторить ошибку §5.

Два побочных наблюдения, записанные без причинных претензий: VM стоит ~35% wall на idle, но её
контейнер показывает *меньше* react-выбросов, чем нативный прогон (возможно, cgroup `--cpus 8`
уменьшает межъядерную миграцию — не проверялось); и аудит правильно отметил оба возмущённых
нативных прогона — методология работает независимо от того, откуда родом остановки.

**Следствие для опубликованных результатов: никакого.** Протокол «7 повторов + прожиг +
peer-аудит» (BENCHMARK.md §2) защищает от этих остановок одинаково, идут ли они из VM или из
хоста под ней.

## 7. Полные результаты — сравнение E-2

Исходная матрица на момент аудита: run id `20260730T051524Z` — с тех пор **вытеснена**
семиповторной матрицей `bench/results/20260730T220711Z`, на которой E-2 пройден полностью
(BENCHMARK.md §9); эта секция фиксирует состояние на момент аудита. Вытесненные сырые серии
утилизированы после переработки (её `flame/`-профиль сохранён — он по-прежнему источник
атрибуции §8; серии восстановимы из git-истории). Перцентили — точные ранги,
индекс `ceil(p·n) − 1`, без интерполяции. M1 скорректирован по CO (`done − intended`).

### 7.1 Критерий дословно

> **FALSIFIER (E-2).** Against the real C++ engine in-container, §5.2 harness: if
> picows+uvloop+msgspec **fails to beat** websockets+asyncio+stdlib by **≥5 µs p50 AND ≥20 µs
> p99.9** with run-to-run variation smaller than the gap, the product client reverts to websockets
> everywhere.
>
> — `docs/decisions/02-decision-record.md:55`

E-2 — это **триггер отката**, а не критерий прохождения. Он срабатывает, когда tuned проигрывает.

### 7.2 Результат — откат не срабатывает

| Сценарий / метрика | полоса naive (µs) | полоса tuned (µs) | Δ медиан (µs) | худший разброс (µs) | разброс < Δ? | полосы не пересекаются? |
|---|---|---|---:|---:|:---:|:---:|
| idle p50 | 86.6 – 88.2 | 59.0 – 60.7 | **27.6** | 1.7 | ✅ | ✅ |
| idle p99.9 | 174.1 – 186.3 | 134.4 – 144.3 | **43.4** | 12.2 | ✅ | ✅ |
| react p50 | 169.6 – 172.1 | 127.2 – 128.5 | **42.8** | 2.5 | ✅ | ✅ |
| react p99.9 | 706.6 – 745.7 | 567.3 – 595.3 | **146.4** | 39.1 | ✅ | ✅ |
| paced p50 | 603.4 – 700.2 | 39.7 – 40.3 | **586.5** | 96.8 | ✅ | ✅ |
| **paced p99.9** | **2 097.1 – 5 782.8** | **186.5 – 198.8** | **1 923.5** | **3 685.7** | ❌ | ✅ |

Требуемые пороги: ≥5 µs p50, ≥20 µs p99.9. **Каждая ячейка перекрывает оба с большим запасом, во
всех трёх сценариях.** Ни одно условие отката не выполнено.

### 7.3 Единственная ячейка, задевающая оговорку о стабильности

`paced p99.9` — единственный провал, и его причина определима: **нестабилен хвост самого
naive-арма.** Базовая линия, работающая примерно с половиной периода запаса, имеет внутренне рваный
хвост. Нестабильность — свойство измеряемого, а не измерения; чистый хост её не исправит и не
должен.

Оговорка существует, чтобы не заявить разницу, которую мог бы объяснить шум. Эта цель достигается
более сильным тестом: **полосы полностью не пересекаются.** Худший tuned paced p99.9 (198.8 µs)
лучше лучшего naive (2 097.1 µs) более чем в десять раз. Шум такого не создаёт.

Поэтому улучшение paced p99.9 сообщается **полосой, а не точечной оценкой**.

### 7.4 Две разные нестабильности, ранее слитые в одну

Прежняя отчётность сводила их к одной строке («E-2 провален»), что преувеличивало проблему:

| | Ячейка | Причина | Лечится чистым прогоном? |
|---|---|---|---|
| **A** | paced p99.9 | Собственный хвост naive-арма | **Нет** — это и есть результат |
| **B** | idle / react p99.9 в *некоторых* матрицах | Остановки платформы (§5, механизм не доказан) | **Да** — peer-аудит + перепрогон |

Предметом текущей работы является только **B**.

|---|---:|

### 8.5 Раскрытие по E-4

- **E-4a — idle M1:** порог «tuned p50 ≲ 80 µs и межпрогонный разброс p50 ≲ 20 µs».
  Результат 59.4 µs, разброс 1.7 µs — **проходит.**

Все межпрогонные разбросы p50 ≤ 1.7 µs, поэтому вторая оговорка не задевается нигде.

## 9. Peer-аудит

Построен после того, как выяснилось: предстартовая защита структурно неспособна поймать остановку,
начинающуюся через семь минут после старта на простаивающей машине. Аудит сравнивает повторы между
собой *постфактум*, по признакам, независимым от самой латентности.

| Правило | Условие | Калибровка |
|---|---|---|
| **WALL** | `wall_s > медиана(wall соседей) × 1.10` | Чистый idle: CV по wall ≈ 0.7%; загрязнённый был +17% |
| **TAIL** | `n_above_5ms > max(20, 2 × медиана(счётчиков соседей))`, и превышение ≥ 20 | Загрязнённый прогон нёс 24 против 0 у соседей |

Фальсифицирован в обе стороны: отметил ровно `idle_tuned_R1` (wall на 17.1% выше медианы соседей;
`n_above_5ms` = 24 > порога 20) и пропустил остальные 21 прогон.

**Почему это не подгонка под результат:** оба признака независимы от публикуемого распределения
латентности. Прогон исключается за то, что при одинаковой работе занял больше времени, чем соседи,
а не за то, что дал нежелательное число.
